# Japanese Tech Generation

## 目的

日本語の技術文書を新規に生成するとき、論理の順序と言葉の自然さを両方整える。
読者が語句の関係を補い直したり、前の文へ戻ったりせず、段落単位で理解を進められる文章を作る。

このSkillだけで新規生成を完結させる。
一般的な日本語ライティングSkillを自動で追加せず、生成後の別工程もユーザーが求めた場合だけ実行する。

## 適用範囲

使う場面:

- 技術書の章・節・コラムを書く
- 技術記事、解説文、設計判断の説明を書く
- 調査結果や実装方針を読者向けの本文に変換する
- メモや箇条書きから、論証を持つ日本語本文を生成する
- 読者の知識に合わせて、新しい説明文を書く

使わない場面:

- 一、二文の短い返答
- コード、設定、コマンド出力が主役の回答
- 文章レビューだけを行う依頼
- 既存原稿の推敲や論理修正が主目的の依頼

## 生成手順

1. 読者、読む目的、文書種別、既知としてよい事項、説明が必要な事項、語調を短く定める。
   依頼と会話から判断できる前提は使い、架空の人物像を補わない。
2. 読者が理解するために必要な順序を決める。
   報告や設計説明では結論を先に示し、その理由を続けるなど、依頼と用途に合わせる。
   同じ結論を繰り返すための前置きや、結論を隠すための演出は加えない。
3. 説明を進める段落について、前段から受ける問い、その段落で加える内容、次に必要になる説明を短く決める。
   一段落には一つのトピックを置く。
4. 新しい概念は、何の種類に属するものかを先に示し、用途や性質を説明する。
   用語、理論、引用、例は、後続の理解や判断に必要なものだけを導入する。
5. 下の「自然な日本語にするための判断基準」に従って本文を書く。
   言い換えや省略の判断に迷う場合は、[具体例](references/natural-japanese.md) の該当箇所を読む。
6. 根拠と本文を照合し、事実、推測、提案、例の仮定を区別する。
   因果を説明する場合は、根拠のある仕組みと適用条件を示す。
   資料にない理由や数値を、文章を滑らかにするために補わない。
7. 「自己点検」に沿って読み直し、意味の飛躍、不要な重複、読みにくい表現を直す。

初心者向け、専門外の読者向け、ジャーゴンを避ける依頼では、中心語彙を先に列挙する。
各語について、読者が既知か、初出で何を説明するか、後続のどの判断に使うかを決めてから本文を書く。
本文で再利用しない専門語は導入せず、具体的な説明のまま残す。

## 自然な日本語にするための判断基準

### 語の組み合わせと意味関係

- 分野で定着した語と動詞を選ぶ。
  名詞を重ねて「実施する」「行う」を添えた表現は、動作を直接書けるか見直す。
  専門用語や漢語を一律に平仮名や独自の訳語へ置き換えない。
- 助詞と述語で、誰が何をどうするか、何と何がどのような関係にあるかを明確にする。
  長い修飾句は分け、修飾する語を対象の近くに置く。
- 英語から直訳した比喩や擬人化で、処理や結果を曖昧にしない。
  主体、対象、実際に起きることを具体的に言い直す。
  日本語で定着した表現、無生物主語、受動態そのものは禁止しない。

### 情報の順序と省略

- 読者が知っている対象を足場にして、新しい説明を加える。
  段落の関係は内容と順序で作り、接続詞は因果、対比、話題の切り替えが伝わりにくい箇所に置く。
- 文脈から一意に分かる主語や対象は省略してよい。
  対象が切り替わる箇所や、複数の候補がある箇所では名前を示す。
  定義済みの中心語は統一し、言い換えで別の対象を指しているように見せない。
- 比較する対象は、同じ観点と対応する文の形で説明する。
  図、表、コードが別の例を使う場合は参照先を明確にし、一方の結果を他方の根拠にしない。

### 文の負担とリズム

- 定義、理由、条件、結果、例外を一文に詰め込まない。
  説明の役割が変わるところで文を分ける。
  同じ話題の文は一段落にまとめ、独立した話題には空行を置く。
- 関連する動作や同じ観点の並列は、一文にまとめてもよい。
  短文だけを並べたり、接続助詞で独立した主張をつなぎ続けたりしない。
  語尾を散らすためだけに、用語、文体、断定の強さを変えない。
- 冗長さは文字数で判断しない。
  対象、条件、因果、適用範囲を読み取るための長さは残す。
  用語の再使用や、定義の後に条件を加える文は、同じ主張の反復と区別する。

### 語調と確かさ

- 会話に近い解説、実験報告、手順書など、用途に合う語調を選び、一つの文書内で揃える。
  「難しいです」のような語尾を一律に禁止せず、前後の意味と流れで判断する。
- 「効く」「強い」のような表現は、読者が共有している意味があれば使える。
  判断に必要な効果や比較条件が曖昧な場合は、何がどう変わるのかを書く。
- 確認したことは明確に述べ、推測には根拠と不確実性を残す。
  例が支える範囲を越えて一般化せず、確認していないことを断定しない。

## 優先順位

- 意味と根拠の正確さを保ったうえで、説明の順序と言葉の自然さを整える。
- 読者の次の理解や判断に必要な情報を選び、その理解に必要な説明は省かない。
- 具体的な関係を示し、名前を付ける必要がある場合に術語を導入する。
- 主張を直接述べ、同じ内容の予告やまとめ直しを重ねない。

## 出力ルール

- 生成物だけを出す。依頼されていない限り、設計メモや自己点検結果は出さない。
- Markdown 文書では、一文ごとに改行し、段落の区切りは空行で示す。
- 見出しは、その節が扱う対象や問いを具体的に示す。
- コード、ログ、設定の断片はコードブロックに置く。
- 断定できない内容は、可能性・推量・仮定として正確に書く。
- 「重要なのは」「多角的に」「正面から」「深掘りする」など、内容を増やさない LLM 口調を使わない。

## 自己点検

出力前に次を確認する。

- 読者が共有している対象から説明が進み、段落ごとの話題と前後関係が分かるか。
- 名詞の連続、不自然な動詞や訳語、翻訳調の比喩によって、意味を補い直す必要が生じていないか。
- 助詞、修飾語、指示語、省略された主語の関係を一度で読み取れるか。
- 文を短くするために条件を落としていないか。関連する短文を不必要に分断していないか。
- 例や引用が、支えたい主張と同じ問いに答えているか。
- 新しい概念の種類が初出で分かり、後続の説明で必要な役割を果たしているか。
- 同じ対象の説明中に別の話題を割り込ませていないか。
- 語調を揃えた結果、推測を事実に変えたり、資料にない因果を足したりしていないか。
- 空虚な強調、同じ主張だけの反復、回収されない前方参照が残っていないか。
