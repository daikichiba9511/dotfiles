# 理解度確認

理解度確認は、本文をもう一度読ませる作業ではない。
本文を閉じた状態で概念を思い出し、因果を説明し、新しい事例へ適用できるかを確認する。

## 問題を選ぶ

最初は前提を持たない概念から確認する。 前提概念を説明できない状態で、後続概念の問題を続けない。

一回の確認では三問から五問を上限とし、一度に一問だけ提示する。 次の種類を順に使う。

1. `recall`：用語の定義または因果を本文を見ずに説明する。
2. `explain`：例の各段階が必要な理由を説明する。
3. `apply`：本文にない新しい事例へ概念を使う。
4. `diagnose`：もっともらしい誤説明の間違いを指摘する。

選択肢を見れば答えがわかる問題だけで理解を判定しない。

## 回答を判定する

`expected_points` と回答を比較し、各点を次のいずれかに分ける。

- 明示的に説明した。
- 別の表現で同じ因果を説明した。
- 述べていない。
- 反対の内容を述べた。
- 回答からは判定できない。

採点基準にない専門知識を要求しない。 正しい語を使っただけで、因果を説明していない回答を `applied`
にしない。 曖昧な回答を善意で補完しない。

## 概念の状態

| 状態                    | 証拠                                           |
| ----------------------- | ---------------------------------------------- |
| `recalled`              | 本文を見ずに定義または因果を説明した           |
| `applied`               | 新しい事例で正しい判断と理由を示した           |
| `misconception`         | 同じ誤った因果または境界を一貫して使った       |
| `prerequisite-gap`      | 問題が依存する前提概念を説明できなかった       |
| `insufficient-evidence` | 短すぎる、複数の解釈ができる、問いと対応しない |

文書全体へ理解度の割合を付けない。 概念識別子、状態、回答から得た証拠、次に確認する問題を記録する。

## 再説明する

`misconception` の場合は、誤った命題を引用して、どの条件または因果が違うかを特定する。
`prerequisite-gap` の場合は、前提概念へ戻る。 `insufficient-evidence`
の場合は、正答を見せずに確認範囲を狭めた一問を出す。

再説明では同じ文を短く言い換えない。
文章、順序図、数値例、コード実行のうち、前回と異なる表現を選ぶ。
再説明の直後に同じ問題を繰り返さず、新しい事例を使う。
