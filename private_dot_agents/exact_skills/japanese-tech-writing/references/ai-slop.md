# AI生成文の読みにくさを直す規則

AIが書いた日本語に出やすい型と、その直し方。型に当たっても、意味を保って自然に言い換えられないなら原文を残す。語の一覧は機械的な置換表ではない。
yomiyasu（MIT, nanaism, https://github.com/nanaism/yomiyasu）の規則から、技術文書の推敲に要る部分だけを抜き出して書き直した。ライセンスの全文は `../LICENSE.yomiyasu` にある。

## 1. 意味を保つ（ほかの規則より優先する）

書き直す前に、原文の次の4点を確かめ、書き直したあとも同じに保つ。

1. 主張: 要点と論理関係。論点を別の概念にすり替えない。
2. 比重: 否定していたものを並列（Aに加えてB）にしない。比較の相手と順位を変えない。
3. 言い切りの強さ: 断定、推量、伝聞、許可（〜してよい）、能力（〜できる）、義務（〜しなければならない）、保証（必ず）の強さを変えない。「〜場合がある」を言い切りにしない。
4. 文の働き: 事実、評価、依頼、予定、仮定、伝聞の区別と時制。完了した変更を予定の「〜します」にしない。

原文、依頼、渡された資料、会話の中の利用者の発言にないこと（動作主、原因、条件、数値、例、専門用語）を推測で足さない。読み取れない箇所は本文を残し、書き手への質問として本文の外に出す。

### 言い直しテスト

型に当たった箇所は、直した案を1つ書き、原文と次の6点を比べる。1つでも変わる案は捨てて原文を残す。通るまで作り直さない。

| 点 | 変わる例（案を捨てる） |
|---|---|
| 何について述べるか | 設計の要は単純さにある → 設計のねらいは単純さだ |
| 何を認め、何を否定するか | 手戻りがなくなったわけではない → 手戻りがなくなった |
| 誰が誰にするか | 田中さんが山本さんに確認を頼んだ → 田中さんが確認した |
| 範囲と条件 | 管理者の場合だけ削除できる → 削除できる |
| 断定・推量・伝聞の強さ | 原因は設定の誤りとみられる → 原因は設定の誤りだ |
| 数値・固有名詞・時期 | 約30件 → 30件 |

語や文を削る案は、削る部分にしかない主張、条件、数値、期限がないかで確かめる。

## 2. 比喩動詞と擬人化

技術的な出来事を比喩の動詞で書いた所は、何がどう変わったかを書くか、ふだんの言い方にする。含み（地味に、うっかり）は別の語で残し、原文より強い確度の語（確実に、必ず）は足さない。「骨が折れる」のような定着した慣用句は残す。

| 型 | 直し方の例 |
|---|---|
| 効く、効いてくる | 何がどう良くなるかを書く（目立たないながらも役に立つ） |
| データやシステムが壊れる | 同じ広さの語にする（おかしくなる、使えなくなる）。整合性の話と分かるときだけ「整合性が失われる」 |
| 静かに壊れる、黙って無視される | 気づかないうちに〜、知らないうちに〜。通知やエラーが出ないと分かるときだけ「エラーを出さずに」 |
| 〜側に倒す | 〜を優先する、〜にそろえる |
| 時間を溶かす | 時間を費やしてしまった（後悔の含みを残す） |
| 1つずつ潰す | 1つずつ直す、取り除く |
| 〜に踏み込む | 詳しく調べる |
| 〜した瞬間 | 〜するとすぐに、〜した時点で |
| 前提が崩れる | 何が成り立たなくなったかを前後の文から書く。なければ残して尋ねる |

道具や概念に感情や意志を持たせた文（コードが語る）は直す。働きを客観的に述べる非生物主語（このツールはログを集める）と、設計の用語（責務を持つ、依存する）は残す。

## 3. 大げさな名詞、直訳語、詰まった漢語

- 決まりを「契約」、原文を「正本」、確認を「ゲート」、一覧を「台帳」、考え方を「〜のOS」と呼ぶ語は、実際の役割の語に直す。正式な名称や定着した用語（品質ゲート、会計の台帳）は残す。
- 英語を一語ずつ写した語（この版では → このバージョンでは、回帰が出た → リグレッションが起きた）は、その分野の人が自分で書く呼び名にする。語を差し替えるだけで済まないときは、何が何をどうするかを文として書き直す。
- 「〜を実施する」「〜することが可能です」「担保する」のような中身のない硬い言い回しは、動作と条件が原文にあるときだけ動詞の文にする。文書でふつうに使う漢語（確認する、停止する）は和語に替えない。書き直した所に、原文にない漢語や名詞化を足さない。

## 4. 否定対比と前置き、締め

- 否定対比（AではなくB）は、Aを外しても主張が変わらないときだけBだけの文にする。誤解を正す否定（原因はキャッシュではなくDNSの設定だった）は残す。Aを「Aに加えてB」のように肯定の側へ移さない。
- 否定と肯定を2文に分けた形（必要なのは新しい道具ではない。使い方をそろえることだ。）は、否定を残して1文にまとめる。
- 中身を予告するだけの前置き（重要なのは、結論から言うと、ポイントは3つです）は、予告の重みを述語に残して続く文とまとめる。数の予告は、数と項目が合うときだけまとめる。
- 本文で言い終えたことを言い直すだけの締め（まとめると、いかがでしたでしょうか、ぜひ試してみてください、参考になれば幸いです）は削る。削る前に、そこにしかない数値や条件がないかを確かめる。

## 5. 書式

- 箇条書きの先頭の太字ラベルとコロン（`- **応答速度の低下**: ピーク時に3秒を超えた。`）は、ラベルが説明をまとめただけの語なら、太字とコロンを外してラベルの意味を説明の文に入れる（`- 応答が遅くなり、ピーク時に3秒を超えた。`）。値の項目（期限、担当、数値）と、名前に説明が続く項目（引数、設定項目）はラベルとコロンを残し、太字だけを外す。番号と項目の数と順は保つ。
- 太字は用語の初出の定義など、外すと読み違える所だけに残す。
- 絵文字、地の文のダッシュ（—、―、──）、文末を飾るコロンは外す。ダッシュを外して前の条件が後ろまで掛かるなら2文にする。コード、URL、図の罫線、ラベルと値のコロンは残す。
- 見出しは、その節で何を扱うかが分かる短い項目名にする。見出しから外した警告や条件は本文に移して残す。

## 6. 読点

短い主題や主語、目的語（今回は、これを）のすぐあとで間を作るだけの読点は外し、新しく足さない。次の読点は残す。

- 誤読を防ぐ読点（店長は、慌てて逃げた客を追いかけた）
- 主題のあとに別の動作主が続く所（会議では、担当者が説明した）
- 長い主語や節のあと、定義の「〜とは、」のあと
- 並べた語句の間、条件・逆接・理由の切れ目、文頭の接続語（まず、また）のあと

外すのは読点だけで、語順と述語は変えない。

## 7. 1か所ずつ直す

sed や正規表現の置換で本文をまとめて直さない。同じ形の箇所が続いても、前後の文を読んで1か所ずつ直すかを決める。
