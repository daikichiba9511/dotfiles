# 読者の前提から日本語を書く

**読者前提**とは、その文書を読む人の役割、読む目的、すでに知っている事項、本文で説明が必要な事項をまとめたものを指す。
架空の経歴や性格を加えず、依頼、資料、既存文書から確認できる範囲で定める。

**ジャーゴン**とは、特定の集団では通じても想定読者には意味が定まらない語、または指す対象を特定せず専門的な雰囲気だけを加える語を指す。
必要な専門用語は、指す対象と必要性を確定し、初出で説明すれば使ってよい。
ジャーゴンは言い換えるか削除する。

## 併用する規範

作業前に `../japanese-tech-writing/SKILL.md` を読む。
まとまった技術文書を新規生成するときは `../japanese-tech-generation/SKILL.md` も読む。
章、記事、解説文など、読み物としての流れが必要な文章では、構成を決める前に [認知リズムの規範](references/cognitive-rhythm.md) を読む。
設計資料、手順書、障害報告では、正確さと検索しやすさを優先し、認知リズムの規範から「事実に基づく認知の切替」と「進行実況の削除」だけを適用する。

## 本文より先に読者前提と用語を固定する

まとまった本文を一文字も書く前に、次の二つの表を作る。
成果物をファイルに保存する場合は、同じディレクトリへ `reader-term-contract-<slug>.md` として先に保存し、`shasum -a 256 <path>` でハッシュ値を記録する。
チャットだけで完結する場合は、Codex の commentary で本文より先に独立した作業結果として提示し、final の本文へ表を再掲しない。
ユーザーが本文だけを求めた場合も表は作るが、表の提示が不要だと明示された場合は作業用として保持し、本文だけを返す。

### 読者前提表

| 項目 | 内容 | 根拠 | 不確実な点 |
|---|---|---|---|
| 読者の役割 |  |  |  |
| 読後に行う判断または作業 |  |  |  |
| 既知としてよい事項 |  |  |  |
| 説明が必要な事項 |  |  |  |
| 資料にないため確定できない事項 |  |  |  |
| 適切な具体例 |  |  |  |

読者の年齢、職歴、性格など、説明の選択を変えない属性は書かない。
読者が不明な場合は、依頼を実行できる範囲で最も前提知識の少ない読者を仮定し、その仮定を「不確実な点」に書く。
読者の違いによって結論、用語、説明量が大きく変わる場合だけ、本文生成前に確認する。

### 用語対応表

| 出典 | 文書内の目的 | 具体的に指す対象 | 役割 | 読者の既知・未知 | 初出で説明する内容 | 候補語 |
|---|---|---|---|---|---|---|

列順を変えない。
「具体的に指す対象」と「役割」を埋めるまで、「初出で説明する内容」と「候補語」は空欄にする。
役割は `条件 / 状態 / 出来事 / 値 / 記録 / 目的 / 手段 / 対象` から選ぶ。
同じ候補語が異なる対象や役割を指す場合は行を分け、原則として別の語を選ぶ。
通常は一つの節につき一行から六行に収め、超える場合は扱う問いが変わる境界で表を分ける。

## 用語を選ぶ

次の順で選ぶ。

1. 読者がすでに使っている語を優先する。
2. 分野で意味が確立している語を使う。
3. 普通の日本語で具体的に書けるなら、専門的に見える言い換えを作らない。
4. 新しい名前が後続の説明や判断を短く正確にするときだけ、名前を導入する。
5. 名前の必要性を説明できなければ、具体的な記述のまま書く。

漢字の熟語を一律に避けない。
想定読者にとって日常語ではない熟語、分野固有の意味を持つ熟語、意味の範囲が複数ある熟語は説明対象にする。
略語は初出で正式名称と本文中での意味を示す。
英語やカタカナ語は、定着した日本語で同じ意味を正確に表せる場合、日本語を使う。
ただし、独自の直訳で定着語を置き換えない。

「文脈」「レイヤー」「最適化」「本質」「仕組み」「観点」のように広い意味を持つ語は、それだけで禁止語にはしない。
その文で何を指すか一つに定まらない場合、または具体的な対象へ置き換えても意味が変わらない場合は、具体的な記述へ直す。

## 初出で定義してから使う

新しい語は、使用前または初出の同じ文で説明する。
初出より前に見出し、図表、要約、コード識別子へ出さない。

定義は次の順で書く。

1. 「Xとは、Yを指す」の形で、指す対象または判定条件を示す。
2. 読者が「何のために区別するのか」を必要とする場合だけ、文書内の役割を続ける。
3. 境界が誤解されやすい場合だけ、含む例と含まない例を一つずつ示す。

定義文の中に、読者前提表にも用語対応表にもない専門用語を入れない。
別の専門用語が必要なら、その語を先に定義し、依存順に並べる。
同じ語を言い換えただけの循環した定義を使わない。

## 本文を書く

本文の中心語彙は用語対応表に載せた語と、読者前提表で既知とした語に限る。
具体的な出来事、数値、操作、発言を先に示し、それらをまとめる必要が生じた位置で専門用語を導入する。
読者が結論を受け入れるために必要な順序で説明し、用語の紹介順を文章の都合だけで入れ替えない。
定義した語は同じ意味で使い続け、途中で広い意味や狭い意味へずらさない。

読みやすくするために、資料にない日付、数値、原因、構成要素、利用者の行動を補わない。
現在日時や一般的な事例から補った内容を、その案件の事実として書かない。
資料から確認できる事実、事実から導いた推定、今後の提案を文の述べ方で区別する。
推定には根拠と不確実性を示し、確定に必要な情報がなければ「確認できない」と書く。

用語の定義だけを連続させない。
定義の直後に、その語が実際の判断、比較、操作のどこで必要になるかを示す。
用語を再利用しないなら、その用語を削り、具体的な説明へ戻す。

## 出力前に監査する

草稿の見出しと本文から、漢字の専門語、長い名詞句、略語、英字、カタカナ語、引用符で囲んだ名前を拾い、次の順で確認する。

1. **既知確認**：読者前提表で既知としたか、初出で定義したか。
2. **指示対象確認**：各語が用語対応表の「具体的に指す対象」へ一意に戻るか。
3. **定義の閉包確認**：定義に使った語も、既知または定義済みか。
4. **必要性確認**：その語が後続の判断、比較、操作に使われるか。
5. **置換確認**：具体的な記述へ戻して意味が変わらないなら、専門語を削れるか。
6. **一貫性確認**：同じ語を同じ意味で使い、異なる役割へ流用していないか。
7. **読者確認**：例、説明量、文の長さが読者の目的と前提知識に合うか。
8. **雰囲気語確認**：対象、条件、因果を増やさず専門的な印象だけを加える語が残っていないか。
9. **出典確認**：日付、数値、原因、構成要素、影響が資料から確認できるか。推定や提案を事実として書いていないか。

一つでも説明できない語があれば、定義を足すことから始めない。
まず、その語が必要かを判定し、不要なら削除する。

## 誤りを見つけたとき

読者前提や具体的に指す対象が誤っていた場合は、本文へ弁明を足さない。
表の該当行を直し、その行に依存する段落を生成し直す。
本文を書き始めてから表を作っていないことに気づいた場合は、表を後付けして続行せず、草稿を破棄して表から再開する。
